# 网盘请求限流：匀速、保存即生效、参数名副其实

2026-10-02 评审设置页「下载限流配置」的三个参数和底层机制之后定的方案。目标三件：请求匀速发出去、改了设置不用重启、
三个参数管的范围和名字对得上。**方案先给用户看，同意后再动手。**

## 现状（逐条核过代码；带数字的是照现有搭法拿假请求量的，探针没留在仓库里）

**机制**（`services/download/rate-limited.ts`）：每个账号一把「每秒配额」（Bottleneck 的 reservoir，每 1000 ms 补满），
每个账号 × 通道一把并发限流器（`normal` / `life` / `offline` / `download`），全部链在每秒配额上。
115 的所有接口走 `request115`、夸克的所有接口走 `quarkRequest`、OpenList 只有取直链走；同步任务的文件下载走 `download` 通道。

按账号隔离、每个请求有超时和取消所以槽位一定会还、重试会重新排队、没救的失败不重试——这些是对的，不动。

**问题**：

1. **保存后不生效。** 三个值只在限流器第一次创建时读（`rate-limited.ts:48`、`:75`）。重建用的 `clearRateLimiters()` 只挂在
   `POST /api/clearRateLimiters` 上，没有任何地方调。v1 保存设置时会调（0ef8d10），移到 v2 后端时丢了；
   设置页那段 409「有任务正在执行中，无法保存设置」（`settings/page.tsx:369`）是当时留下的死代码。
2. **名字和实际管的对不上。**

   | 界面上的名字 | 键 | 实际管的 |
   |---|---|---|
   | 链接获取每秒请求数 | `linkMaxPerSecond` | 这个账号所有接口请求（列目录、整理、转存、监控、云下载；302 取直链在代理进程里另算一份，见第 10 条）加上每个文件下载的开始，共用的每秒配额 |
   | 链接获取并发数 | `linkMaxConcurrent` | 所有接口请求的并发；`normal` / `life` / `offline` 三条通道各有一份，一个账号实际最多是它的 3 倍 |
   | 文件下载并发数 | `downloadMaxConcurrent` | 只管同步任务里的下载；监控触发的下载不走它（`life/handlers.ts:155`）；单个任务被写死的 `mergeMap(…, 10)` 封顶（`task/runner.ts:411`），表单却收到 50 |

3. **并发基本是摆设。** 下载开始也扣每秒配额，一个文件扣两次（取直链、开始下载）。每秒 2 时小文件就是每秒 1 个左右：
   2 / 2 / 5 和 2 / 10 / 50 量出来都是 1.08 个文件 / 秒。
4. **一秒发一批，不是匀速。** 「每秒 2」下 6 个请求的发出时刻是 913、915、1006、1008、2008、2009 ms：100 ms 里出去 4 个。
   Bottleneck 自己的文档写着 reservoir 是给「要成批发」的场景用的，平滑限速用 `minTime`。
5. **取值范围。** 表单是整数、每秒 1–100、并发 1–50：慢于每秒 1 次填不出来。后端只要求正数（`schemas/entities.ts:248`）：
   直接调接口填 0.5，这个账号的请求全部永远排队（每秒 0.5 和并发 0.5 都实测过）。
6. **默认值三处各写一份，已经不一致。** 建库和后端兜底是 2 / 2 / 5（`db/defaults.ts:19`，各调用点还各有一个 `?? 2` / `|| 2` / `|| 5`）；
   设置页的占位和兜底（`settings/page.tsx:216`）、README（`Readme.md:453`）写的是 2 / 10 / 2。建库时写进去的是 2 / 2 / 5，
   所以没改过设置的库里实际生效的是 2 / 2 / 5，错的是占位和文档。
7. **没有优先级。** 界面上的操作（浏览目录、转存、整理预览）和后台批量活排同一个先进先出的队。同步任务跑着时插进一个接口请求要等 7.6–8.7 秒。
   收藏夹抄目录靠 `accountBusy` 每 250 ms 看一眼来让路，是手工补的一处。
   **更正（实施时才发现）**：评审时把 302 起播也算了进来，错了——302 在代理进程里，不和同步排队，见第 10 条。
8. **限流器和下载函数住在同一个文件里**，而下载函数要 import 网盘注册表：`cloud-115/client.ts → rate-limited.ts → drive/registry →
   115 的 Provider → cloud-115/share.ts → client.ts` 成环（`client.ts:61` 那段 ShareBusyError 的注释说的就是它）。
9. **键靠字符串拼接再 `split(":")[0]`。** 账号名没有禁止冒号，`a:1` 和 `a:2` 两个账号会共用一个每秒配额。
10. **限流器是进程里的，而进程有两个**（评审时漏了，做到第 4 步前才发现）。Emby 代理是独立进程（`src/proxy.ts`，只读库），
    302 取直链在它那边另有一套限流器：同一个账号，同步在 API 进程按每秒 N 个发，起播在代理进程另按每秒 N 个发，互相不排队，
    合起来最多是设置值的两倍。这是既有的拓扑（「管理端崩了也不影响播放」），不动；但它带来两个后果：
    保存设置时在 API 进程里通知一声到不了代理进程；「302 起播排在同步后面」这个问题本来就不存在。

## 定下来的口径（按推荐；不同意哪条先说）

1. **每秒配额换成请求间隔**（Bottleneck 的 `minTime = 1000 / 每秒请求数`）：匀速、能慢于每秒 1 次、可以原地改。
2. **下载不占接口配额。** 下载打的是 CDN 不是接口；每个下载都要先取到直链，取链是匀速的，所以下载开始的频率本来就不会超过每秒请求数
   （重试除外）。这样「文件下载并发数」才有意义，同样的设置下小文件会快一些。
   **代价要看清**：以前同步下载时有一份额度被下载的开始占着，接口请求实际到不了设置值；改完是实打实的设置值，
   而设置值没变，老用户不会察觉。列目录、整理这些不下载的活一直就是设置值，没有变化。
   （写方案时按「一个文件一个接口请求」估的是快一倍、接口频率翻倍；真机上 115 一个文件要 3 个左右接口请求，实际是三成，见进度。）
   不想要这个变化，就保留「下载也占配额」（只是文案照实写），其余各步不受影响。
3. **每秒请求数可以填小数**，范围 0.1–100（0.5 = 两秒一个）；两个并发仍是 1–50 的整数。后端校验和表单一致。
4. **「文件下载并发数」管所有文件下载**：同步任务的外层上限跟着设置走，监控触发的下载也进 `download` 通道。
5. **设置的键跟着语义改名**（2026-10-02 用户确认：已经偏离语义的可以改）。整组 `download` → `throttle`；
   `linkMaxPerSecond` → `requestsPerSecond`、`linkMaxConcurrent` → `requestConcurrency`、`downloadMaxConcurrent` → `downloadConcurrency`。
   迁移 0021 把库里 `app.download` 那一行换成 `app.throttle`。降级回旧版本会回到默认值（旧版不认新键）。
6. **默认值以实际生效的 2 / 2 / 5 为准**，只留后端一份；`GET /api/settings` 回的 `throttle` 总是补齐的，前端不再有自己的兜底数字。
   不放进 `@openstrm/shared`：它是纯类型包（v2 架构约定）。上下限前后端各写一份、注释互指，是仓库里现成的做法。
7. **这一节改名「网盘限流」**（锚点 `throttle` 不变）；`POST /api/clearRateLimiters` 删掉（没人调，改成原地生效后也没用了）。

## 方案：四步，各一个提交（前三步做了，第 4 步没做，见各节和末尾「进度」）

### 1. 限流器搬成中立叶子 `services/throttle.ts`（`refactor(throttle)`，不改行为）

- 新文件只依赖 bottleneck、rxjs 和设置仓库，不 import `drive/`。内部是 `Map<账号名, { pace, channels: Map<通道, 限流器> }>`，
  不再拼字符串、不再 `split`。没带账号的请求照旧共用一个桶。
- 接口：
  - `scheduleForAccount(account, channel, fn, signal?)`、`enqueueForAccount(account, channel, fn)`：调用方只说账号和通道，
    不再自己读设置、传并发数。`ThrottleChannel = "normal" | "life" | "offline" | "download"`；`download` 用文件下载并发，其余用接口并发。
  - `throttleSettings()`：读设置、补默认、夹进上下限（并发取整）。四个调用点各自的 `?? 2` / `|| 2` / `|| 5` 全部删掉。
  - `accountBusy(account)`、`resetThrottle()`（原 `clearRateLimiters`：让旧的排空再丢，测试之间用）。
- `db/defaults.ts` 导出 `THROTTLE_DEFAULTS` 和 `THROTTLE_LIMITS`（它本来就是默认设置的家，没有别的 import），建库、`throttleSettings()`、
  第 2 步的 zod 校验都用它。
- 改 import 的：`cloud-115/client.ts`（`request115` 去掉没人传的 `maxConcurrent` 选项，`limiterChannel` 收成 `ThrottleChannel`）、
  `quark/client.ts`、`drive/providers/openlist.ts`、`download/rate-limited.ts`（只剩取直链 / 下载 / 写 strm）、`library/indexer.ts`、
  `routes/system/clear-rate-limiters.ts`。`client.ts:61` 那段说 import 环的注释跟着改（经限流器的这一环断了；ShareBusyError 不挪）。
- 测试：`download/enqueue.test.ts` 搬成 `services/throttle.test.ts`，并发数改成写设置再 `resetThrottle()`；另外五个 itest
  （`directory/remote`、`task/runner`、`quark/client`、`quark/share`、`download/rate-limited`）只改函数名。
- 这一步仍是 reservoir、下载仍链在配额上；唯一的行为差别是病态取值（并发 0.5 这类）被夹到下限，不再把账号卡死。

### 2. 机制：匀速、下载不占配额、保存即生效（`feat(throttle)`）

- `pace` 换成 `new Bottleneck({ minTime })`，`minTime = Math.round(1000 / linkMaxPerSecond)`；`download` 通道不再链到 `pace`。
- `applyThrottleSettings()`：对已建好的限流器原地 `updateSettings`（`pace` 改 `minTime`，各通道改 `maxConcurrent`）。
  `PUT /api/settings` 里 `patch.download` 有值时在 `patchAppSettings` 之后调。排队中的、在跑的活都不受影响，不需要 v1 那个 409。
- 删 `POST /api/clearRateLimiters`（路由文件和 `index.ts` 里的注册）。
- 后端校验（`schemas/entities.ts`）：`linkMaxPerSecond` 是 0.1–100 的数，两个并发是 1–50 的整数，带中文提示。
- `GET /api/settings`：`download` 用 `throttleSettings()` 补齐后再回。
- 同步任务（`task/runner.ts:411`）：写死的 10 换成 `文件下载并发数 + 接口并发数`，任务开始时读一次（默认 5 + 2 = 7）。
  运行中调大并发，当前这一轮最多涨到这个数，下一轮才完全按新值。
- 监控的下载（`life/handlers.ts:155`）：`downloadFile` 包进 `scheduleForAccount(账号, "download", …)`。监控本身一个一个处理，
  这样做是让它和同时在跑的同步任务共用一个上限。
- `accountBusy` 的含义跟着变成「接口上有没有人在排」：大文件下载期间不再让收藏夹抄目录白等。
- 测试（`services/throttle.test.ts`，间隔都用 10–50 ms 级，断言留余量）：
  - 匀速：相邻两个请求的间隔不小于设定值；闲一阵之后来一批也不成批发；
  - `minTime` 换算：每秒 0.5 → 2000 ms、每秒 100 → 10 ms（纯函数，不真等）；
  - 原地生效：队列里有活时改每秒请求数和并发，之后按新值走、活全部跑完（钉住「改完不会卡死」）；
  - 下载通道不占配额：每秒请求数很低时，5 个下载任务同时开始；
  - 账号名带冒号：`a:1` 和 `a:2` 各走各的；
  - 设置路由（itest）：0.05、并发 1.5 回 400；合法值保存后 GET 回的是补齐的值，已建好的限流器按新值走；
  - `runner.itest` 的取消用例：改成写设置 + `resetThrottle()`，断言不变。

### 3. 键改名、设置页和文档（`feat(settings)`）

- 改名（口径 5）：`packages/shared` 的类型（`ThrottleSettings`）、`db/defaults.ts`、`services/throttle.ts`、`schemas/entities.ts`、
  设置路由、用到旧键的测试，以及迁移 `0021_throttle_settings.sql`（只动数据：`app.download` → `app.throttle`，三个字段换名）。
  第 1、2 步先用旧键，改名集中在这一步，前后端一起换。
- 小节标题「网盘限流」，节首一句：每个网盘账号各算各的，保存后立即生效；被网盘风控过就把每秒请求数调小。
- 三个字段（定稿时再顺一遍文案）：
  - **每秒请求数**：每个账号每秒最多发几个接口请求，列目录、取直链、转存、整理、监控都算。可以填小数。
    输入框下面跟着算一句「约每 500 毫秒一个」/「约每 2 秒一个」。
  - **接口并发数**：每个账号同时在路上的接口请求数。监控和云下载各有自己的一份。
  - **文件下载并发数**：每个账号同时下载几个文件（字幕、nfo、图片这类）。下载不占每秒请求数。
- 表单：每秒请求数收 0.1–100、最多两位小数；`fromSettings` 里的 `?? 2` / `?? 10` / `?? 2` 和三个数字占位删掉；409 那段死代码删掉。
  上下限在前端写一份，注释指向 `db/defaults.ts`。
- `packages/shared/src/types/settings.ts:71` 的注释改成实际含义；README 第 453 行改成新名字、正确的默认值和「保存即生效」。

### 4. 界面上的操作不排在同步后面（**没做，等用户定**）

原方案是「交互请求插队」：`AsyncLocalStorage` 标记 + Bottleneck 高优先级，包 302 取直链和界面浏览目录两处。
动手前发现前提错了一半（现状第 10 条）：302 在代理进程里，本来就不和同步排队，包它没有任何效果；剩下的只有
「同步下载跑着时，界面上对同一个账号的操作要多等几秒」这一件事，而且只包浏览目录一处的话，转存、整理预览照样等。

模拟的数字仍然成立，但说的是 **API 进程里**插进来的一个接口请求（同样每秒 2，下载型同步在跑）：

  | | 文件 / 秒 | 插进来的接口请求等待 |
  |---|---|---|
  | 改之前 | 约 1 | 7.6–8.7 秒 |
  | 第 2 步之后 | 约 2 | 3.2–3.6 秒 |
  | 再加优先级 | 约 2 | 0.9–1.2 秒 |

要做的话换个方向更值：不是给界面请求标「高」，而是给同步任务取直链那一处标「低」（`runner.ts` 里包一下 `resolveDownload`）。
这样界面上的所有请求（浏览、转存、整理预览、云下载列表）都自动排到它前面，只改一个调用点；界面请求是零星的，
同步不会被饿死。纯 strm 的同步不取直链，本来就不占队，受益的只是「首次同步、要下几千个 nfo / 图片」这种场景。
代价是仓库里第一次用 `AsyncLocalStorage`（或者给 `downloadLink` 的参数加一个优先级，改三家 Provider 的签名）。
**建议先不做**：第 2 步已经把这个等待从 8 秒降到 3 秒多，等真有人嫌慢再加。

## 不做的、以及为什么

- **风控冷却（被风控后让整个账号停一阵）。** 评审时说过它是个小改，读完分类代码后改口：现在「被风控」是按文案猜的
  （`drive/errors.ts` 的 `classifyAccountIssue`：封控 / 405 / doctypehtml），拿来停一轮同步够用，拿来停整个账号几分钟就太粗。
  115 的 405 还是分接口的：`cloud-115/life.ts` 里 proapi 回 405 就降级到 webapi 照常用，405 不等于账号被封；
  夸克是按 HTTP 403 / 429 判的，403 是不是只代表风控没验证过。要做得先知道被风控时各接口到底回什么。
  等真机上撞到一次，拿当时的日志再定触发条件。
- **分网盘各一套参数**：115、夸克、OpenList 现在共用一组值。没有人提过需要，先不加设置项。
- **重试改指数退避**：现在固定隔 2 秒，重试会重新排队，单机单用户够用。
- **排队等待设上限**：队伍最长也就是同步任务在管线里的那几个文件，等待有上界（默认设置下三秒多），不需要。
- **两个进程共用一个节奏**：API 进程和代理进程各按设置值发，合起来最多两倍。要共用得做跨进程的限流（文件锁或者让代理经 API 取直链），
  和「管理端崩了也不影响播放」冲突；起播取直链本身很稀（还有 15 分钟的直链缓存），不值得。
- **先占下载槽再取直链**（改同步任务的管线结构）：能彻底去掉外层上限，但要动重试语义，这轮不碰。
- **默认值放进 shared**：见口径 6。

## 风险

- **匀速之后，一个操作里连着发几个请求的会慢一点**：每多一个请求最多多等一个间隔（每秒 2 时是 0.5 秒）。浏览很深的目录时能感觉到一点。
- **原地改设置的切换瞬间**：已经排好时间的请求还按旧间隔走完，滞后大约是「接口并发数 × 旧间隔」
  （实测：每秒 2、并发 2 改成每秒 10，约 1 秒后才按新间隔走）。从很慢改快时这段会更长，比如十秒一个改快要等二十秒左右。
- **Bottleneck 的坑**：带 reservoir 的限流器调 `updateSettings()` 会把补额度的心跳停掉（`LocalDatastore._startHeartbeat` 的 else 分支），
  实测改完发完一批就再也不发。新机制不用 reservoir，躲开了；以后别把 reservoir 加回 `pace`，「原地生效」那条测试钉着。
- **升级后同步下载时的接口请求变密**（口径 2）：从设置值的四分之三左右涨到设置值本身（写方案时估的是翻倍，真机更正见进度）。
  每秒 1 个在 115 上跑了两分多钟没有风控；每秒 2 个及以上没试。升级说明里要写明。
- **匀速对「连着发几个请求」的操作更慢**：第一次起播一个没进缓存的文件要 4 个接口请求，就是 3 个间隔——每秒 1 个时等 3 秒，
  每秒 2 个时等 1.5 秒（以前每秒 2 个是先放 2 个、下一秒再放 2 个，最多等 1 秒）。路径进了缓存之后只要 1 个请求。
- **下载的开始不再被间隔拉开**，只受并发限制；频率上界还在（见口径 2）。
- **每次排队前读一次设置**（为了让代理进程也跟上，见进度）：按主键读一行，比以前 `request115` 每个请求把整张设置表读出来再解析要轻。
- **计时类测试**：全量跑、机器忙的时候会抖，间隔和断言都要留余量（`enqueue.test.ts` 里已经踩过一次固定睡 20 ms 不够）。

## 升级说明里要写的

- 限流设置保存后立即生效，不用再重启。
- 「每秒请求数」现在是匀速发，可以填小数（0.5 = 两秒一个）。
- 文件下载不再占每秒请求数：同样的设置下，同步字幕 / nfo 这类小文件快三成左右（115 实测），接口请求的频率也从设置值的
  四分之三左右涨到设置值本身。想保持原来的量，把每秒请求数调到原来的四分之三。
- 设置页这一节改名「网盘限流」，三个值的含义见各自的说明。
- 这组设置在库里换了名字（升级时自动搬过去，值不变）；降级回 2.13 及以前的版本，限流会回到默认值。
- `POST /api/clearRateLimiters` 删了（界面从没用过它）。

**真机数据更正了两处估计**：

- 「同样的设置下小文件快一倍 / 取直链频率翻倍」（口径 2）估高了。115 上一个文件要 3 个左右接口请求（按路径找文件 + 取链），
  以前再加一个「下载开始」是 4 份额度，现在是 3 份：**快三成左右**，接口请求频率也是从设置值的四分之三涨到设置值本身。
  模拟里按「一个文件一个接口请求」算的，所以算出了一倍。
- 「同步跑完，文件完成的节奏约等于每秒请求数」（验证第 1 条）不对：匀速的是接口请求，文件的节奏是它除以每个文件要的请求数。

**还没验的**：夸克上的文件下载（要找一个带字幕 / nfo 的夸克目录）；每秒 2 个及以上时 115 会不会风控（这次只跑到每秒 1 个）；
界面经真实的 `PUT /api/settings` 改设置时在跑的同步跟着变（接口这条路测试里有，真机上用的是脚本直接调同一个函数）。

**和方案不一样的地方**：

- 第 4 步没做，理由和改过的建议见第 4 步那一节。评审时说「302 起播要等 8 秒」是错的。
- 「滞后大约是接口并发数 × 旧间隔」不准：已经排好的请求走完之后，节奏上还预留着一个旧间隔，实际是「排好的请求数 + 1」个旧间隔
  （测试里并发 1、旧间隔 200 ms，改快之后约 400 ms 才按新间隔走）。
- 设置页的上下限没有抽成和后端同名的常量，只在校验函数旁边注释指向 `db/defaults.ts`。
