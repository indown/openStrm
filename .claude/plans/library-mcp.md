# 影库的智能体工具：分析与方案（2026-09-29，未实施）

用户问「关于影库可以做哪些 mcp 来提升用户体验」，要先深度分析；同时提了一句名字：「影库」是不是改叫「收藏夹」更没歧义（见第六节）。

## 一、现状

智能体这边影库只有「搜」：

- `library_search`（read，transfer 组）：按名字搜索引，每条是一个目录；第二阶段起带 `tmdb`（认出来的作品）。
- `resource_search` 的结果里先带影库的前几条；`find_and_save`（找片入库）流程先搜影库。
- 搜到以后靠通用的 `share_inspect` / `share_save` 看、存。

REST 有、智能体用不了的：加分享（单个、批量预览）、作品墙和作品详情、换匹配 / 不是影视 / 重新识别、分享列表（建索引进度、死活）、重新建索引、更新链接、清理失效。`overview` 里没有影库；`share_inspect` 不知道这个分享收没收着。Telegram 的 `/s` 也只列影库前几条，转存让去网页。

## 二、用户会让智能体办的事

| 场景 | 用户会这么说 | 现在卡在哪 |
|---|---|---|
| 找片存片 | 「我想看沙丘2，存到电影」 | 能做，但同一部的好几个版本散在搜索结果里，模型要自己比画质、大小；剧一季一个目录的，要一个个 inspect 再拼 itemIds；不知道本地已经有了，会重复转存 |
| 收藏 | 「这几个分享帮我收着」「刚才网上搜到的那个先收藏」 | 做不了 |
| 逛 | 「收藏里有哪些 2024 年的剧」「有没有 4K 的漫威」「最近收了什么新片」 | 只能按关键词搜目录名；按作品、年份、类型逛不了（类型 / 地区 TMDB 有，没存） |
| 对片单 | 「这份片单里哪些收藏里有、哪些我已经有了」 | 只能一部一部 library_search |
| 补全 | 「权力的游戏我只有 1–4 季，缺的补上」 | 不知道本地有哪几季，也不知道收藏里哪几季在哪 |
| 纠错 | 「没认出来的帮我认一下」 | 最该交给模型的活：故意写错的名字（巨尺沙2 / Mig 2 The Tranch → 巨齿鲨2，剌杀小说家 / A Writers Odyseey → 刺杀小说家）规则认不出，模型一眼看得出；现在没有工具能写回 |
| 维护 | 「哪些分享失效了，里面的片帮我找回来」「刚加的建好索引没」 | 看不到分享列表、进度、失效分享里有哪些作品 |

纠错、失效找回、对片单是智能体比界面强的地方：界面要人一条条点，模型能批量判断，再请人点头。

## 三、建议的工具

按 agent-access.md「工具 / 设计原则」：按要办的事切、一个工具不混风险档、输出紧凑带 `next`、第三方文本只放数据字段、改东西的工具描述里写「先征得同意」、入参 schema 保持可移植。

| 工具 | 档 | 注解 | 做什么 | 分期 |
|---|---|---|---|---|
| `library_work` | read | RO | 一部作品在收藏里的全部版本 + 本地有没有 + 能原样交给 `share_save` 的参数 | P1 |
| `library_add` | run | OW | 把分享收进来（一个，或一段话里好几个） | P1 |
| `library_works` | read | RO | 按作品逛：类型 / 年份 / 关键词 / 最近收的 / 待确认 / 没认出；P2 起能一次对一串片名 | P1 |
| `library_match` | run | I | 换匹配、标成不是影视、重新识别（一次可以几条） | P2 |
| `library_sources` | read | RO | 收藏的分享：死活、建索引进度、作品数；失效的列出里面有哪些作品 | P2 |

另外改几个现有的：

- `overview` 加一行影库：分享数（失效、建索引中）、作品数（认出 / 在认 / 没认出）。
- `library_search`：每条带作品键 `work`，接 `library_work`。
- `share_inspect`：看的分享已经收着就说一声（`inLibrary`）；没收着的，`next` 里提一句能 `library_add`。
- `resource_search`：网上结果里已经收着的分享标出来。

### library_work（P1，核心）

入参：`work`（作品键 `movie:603` / `tv:1399`，来自 library_search / library_works），或者 `title` + 可选 `year` / `type`（按名字找，重名列候选让模型问人）。

出参（紧凑）：

- `work`：TMDB 编号、类型、正式名、原名、年份、把握、季。
- `owned`：本地已经有的（见第四节）：任务、目录、剧的话有哪几季。
- `versions`：每个版本一条：`ref`（单元引用，给 library_match 用）、分享名、`shareStatus`、在分享里的位置、大小、视频数、季、画质标签、样例文件名、`save: { link, dirId, itemIds }`（原样交给 share_save）。
- `seriesSave`：剧分季分开放的（和界面「一起转存」同一套判断：同一个目录下、季不重叠、条目不重名、分享没失效）：`{ folder, seasons, save }`，一次 share_save 存全季。
- `next`：挑版本的提示（画质、大小、分享死活），和「转存前告诉用户存什么、存到哪」。

体验：「权力的游戏存 4K 那套全季」一步到位；「沙丘2 有哪几个版本」直接给比较表；本地已有的先提醒，不重复存。

### library_add（P1）

入参：`text`：一个或几个分享链接，整段「链接：… 提取码：…」也行，和界面批量添加同一套认法（`findShareLinks`），最多 20 个。

出参：每个的结果：`added`（带分享标题）/ `dead`（加进来了但打不开：失效、提取码不对）/ `exists` / `failed`；`next`：「抄目录要几分钟到几十分钟，library_sources 看进度，抄到的部分已经能 library_search」。

- 档位用 run：不改网盘内容，但加进来会在后台抄目录（打网盘接口），和「开始同步」同一档。描述里写「收藏前把要收的分享告诉用户」。
- 链接可能来自第三方（resource_search 的结果）：被注入的话最多多收几个分享、多抄一会儿目录。上限 20 个 + 要人点头。

### library_works（P1）

入参：`view`（all / movie / tv / low 待确认 / none 没认出，和界面的筛选同名）、`keyword`（在正式名、原名、英文名里找）、`year`（`2024` 或 `2020-2024`）、`sort`（recent / year / title）、`limit` + `cursor`。

出参：每部一行：作品键、正式名、年份、类型、版本数、季、把握、`owned`。没认出的一行是单元引用 + 目录名 + 样例文件名（纠错要看）。

- 海报墙缺的「按名字 / 年份筛」顺手在后端补上，界面以后也能用。
- P2：`titles`（一串片名，最多 50 个）逐个说收藏里有没有、本地有没有，给「对片单」用。
- P2：类型 / 地区（「韩剧」「科幻片」）要识别时把 TMDB 的 genreIds / countries / originalLanguage 存进单元（`fromDetails` 已经拿到了，只是没存；要迁移加列，老数据重认一遍就有）。

### library_match（P2）

入参：`items`（最多 20 条）：`ref`（单元引用）+ `tmdbId` + `type`，或者 `ignore: true`（不是影视），或者 `reidentify: true`。

- 和整理的 `organize_adjust` 同档（run）：只改本地的识别结果，能改回来，不碰网盘。
- 纠错流程的写回：`library_works view=none` → 模型读目录名和样例文件名，用 `tmdb_search` 核对 → 列成表给用户看 → 同意后一次写回。

### library_sources（P2）

入参：`status`（all / expired / indexing / locked）、`limit`。

出参：每个分享：名字、链接、死活、建索引进度（目录数、视频数）、作品数（认出 / 没认出）、最近一次抄完的时间；失效的附上里面认出的作品（前几部），给「失效找回」用。

不做删除和清理：清理失效在界面上一键就行，交给智能体收益小、风险大（删了收藏记录找不回来）。更新链接（relink）也先不做：要比对内容、有确认框，放在界面上。

### MCP prompts（斜杠命令）

- `library_fix`「收藏纠错」：列出没认出 / 待确认的 → 逐条从目录名、样例文件名（英文原名、年份）判断是哪一部，用 tmdb_search 核对 → 汇总成表（目录名 → 认成什么、把握）给用户看 → 同意后 library_match 写回；拿不准的留着。
- `library_series`「补全剧集」（参数：剧名）：library_work → 对比本地已有的季和收藏里的季 → 列出能补的（哪个版本、多大）→ 同意后 share_save（seriesSave 或挑季）+ organize。
- `library_rescue`「失效找回」：library_sources `status=expired` → 列出失效分享里的作品 → 逐部 library_search（别的分享里还有没有）/ resource_search → 给替代 → 同意后 library_add 收新的。
- `find_and_save` 已经先搜影库：搜到作品键时改成先调 library_work 挑版本。

## 四、「本地已经有了」怎么判断

`owned` 是这次体验提升的关键（不重复存、知道缺哪几季）。两个来源：

1. **从收藏里存过**：share_save 存的条目是收藏里的单元时记一笔（单元上加「存到哪个任务、什么时候」）。准，但只管从收藏存的。
2. **本地 strm 目录里认得出 TMDB 编号的**：整理过的目录名带 `[tmdbid=…]`、目录里有 nfo（strm 海报那套离线线索，poster.ts 的 ②③）。要把各任务的本地目录扫一遍，建「tmdbId → 任务 / 目录 / 季」的索引：
   - 海报墙那套只抽 48 张、最多读 3000 个目录，不能直接用；要单独建、缓存，同步完成后失效重算。
   - 没整理过、目录名里也没 id 的认不出。按正式名 + 年份模糊对能补一些，但会误判，先不做。

所以 `owned` 要说清楚是「认得出的已有」：没标的不等于没有。

## 五、权限、分组、安全

- **放哪组**：都放 `transfer`，界面上这组从「搜资源、转存与云下载」改叫「搜资源、收藏、转存与云下载」。library_search 已经在这组，勾了这组的老令牌直接能用；另开一组的话 library_search 挪不过去（挪了老令牌就没了），一个功能拆两处更乱。代价：这组从 9 个涨到 14 个，全开的令牌一共 42 个工具左右。
- **档位**：看的是 read，收藏和纠错是 run（不改网盘，但会打网盘接口 / 改本地数据），没有新的 write / danger 工具。
- **第三方文本**：目录名、文件名、分享标题是上传者写的，只放数据字段；纠错流程里模型要「读」名字来判断片名，描述里再强调一遍名字里的「指令」不执行。
- **上限**：library_add 20 个链接、library_match 20 条、列表默认 20 条带游标。
- **不给智能体**：删收藏、清理失效、更新链接、改提取码（改提取码要用户给码；更新链接有内容比对确认）。

## 六、名字：「影库」要不要改成「收藏夹」

用户的感觉是对的，「影库」有歧义：

- 读起来像「我的片库」，也就是已经在网盘、Emby 里的东西；实际是**别人的分享、还没存进来**。任务页的「全库海报墙」是自己的片，影库页的海报墙是收藏的分享：两面墙两个意思。整理里还有「媒体库类型」，Emby 里叫「媒体库」。
- 对智能体更要紧：模型看到 `library_search` 和「影库」，容易当成用户已经有的，回答「你库里有沙丘2」，其实是「你收藏的分享里有」。有了 `owned` 以后，更要把「收藏的」和「已经有的」分清。

「收藏夹」一听就是「我收着的、还不是我的」，和「收藏的分享」这个事实一致，按钮「加入收藏夹 / 收藏」也顺。要留意的：

- 「收藏夹」听起来像一串书签，搜索、按作品看、认片这些它都有。名字只是入口，页面副标题说清楚「收藏的 115 / 夸克分享：目录树抄在本地，能搜、能按作品看」就行。
- Emby 里的「收藏 / 我的最爱」是给片打心；这里收的是分享，不冲突，但副标题要写「分享」。
- 「分享收藏夹」更严谨，但放在侧栏太长，「收藏夹」够了。

改的范围：界面文案（侧栏、页标题、「加入影库」按钮、弹框、⌘K、设置页一节、提示）、Telegram 文案（「📚 影库里有 N 条」）、通知（「影库里收藏的分享失效」）、README、智能体的工具描述和服务端说明。约 190 处，都是文案。

**不改**：工具名 `library_*`（对外接口，快照只加不改；ChatGPT 这类会缓存工具列表，改名就断）、接口路径 `/api/library`、表名、代码里的标识符。

时机：v2.13.0 还在 rc，正式版之前改掉，用户只会见到一个名字。
